# 《國王戰爭》P7 發布、回復與資料營運手冊（候選版）

**僅限測試分支；本文件不構成部署授權。**

## 1. 發布前必要條件

- 遊戲所有者核准正式發布，確認平台／營運費用／變更範圍。
- 所有 CI 需要顯示成功：Release readiness gates、Verify King War fixes、Game balance simulation、安全測試、前端 build、npm audit。
- 人工操作測試：兩名真人跨裝置建立／加入、遊玩、斷線後重連；小螢幕可讀性；無侵入式戰術提示；高負載及伺服器重啟時妥善告知玩家。
- 確認視覺素材、圖片、字體、音效的商業授權；待正式營運前由合適專業人員審核。
- 決定是否收集匿名化統計，告知玩家資料目的、存取限制與留存期限。

## 2. 必要與可選環境變數

| 變數 | 功能 | 安全須知 |
|---|---|---|
| `NODE_ENV` | 正式應為production | 正式服務應提供已建好的 `client/dist` |
| `PORT` | Render 指定服務監聽 Port | 不應硬編寫特定環境的地址 |
| `KW_ALLOWED_ORIGINS` | 可選的 WebSocket／polling 來源白名單 | 正式站建議設為實際網站 origin；無設定保留開發相容模式 |
| `KW_STATE_DIR` | **可選**加密房間快照目錄 | 必須是持久化、非公開靜態目錄 |
| `KW_STATE_KEY` | 64位十六進位文字（32 bytes AES-256金鑰） | 與快照同時備份，金鑰應放受保護環境變數，**不可提交Git** |
| `KW_MATCH_METRICS_FILE` | **可選**匿名化賽局JSONL路徑 | 必須有合法告知、存取控制、保留策略 |
| `KW_RULESET_ID` | 規則版本標籤 | 每次玩法調整都必須更新，避免跨版本混算 |

**風險限制：** 可選快照目前屬單一 Node 進程的最佳努力式恢復；Socket.IO 同機傳輸、程序中的非同步寫入與磁碟故障仍可能造成最後操作未寫入。不能把它視為 ACID 交易資料庫。Render 有無持久化磁碟、是否能多實例水平擴展，必須在正式部署方案內檢查。金鑰若遺失，現有快照無法恢復。金鑰若外洩，應處理所有已保存的快照與重連憑證。

## 3. 上線演練與健康監測

1. 先記錄正式 `main` commit、環境變數設定及上一個可回復部署標識。
2. 在非正式環境使用不同代碼、不同檔案目錄與不同金鑰演練；禁止測試資料與真人正式資料混用。
3. 確認 `GET /healthz` 取得 HTTP 200、`ok:true`。此為**程序存活檢查**，不表示資料庫或多人對局完整可用。
4. 測試2人遊戲回合、魔法／攻擊、斷線恢復、重新部署／重啟後重連（如有啟用快照），與多人操作。
5. 監控錯誤率、CPU、記憶體、WebSocket 斷線率、玩家對局完成率及遊戲伺服器日誌。將上述基準與版本對照記錄。
6. 正式上線前確認正在進行的對局不會被更新意外中斷；無法保證時應事先告知並安排維護時間。

## 4. 發布異常的回復

- 重大異常立即停止新版本流量，回復上一個**已成功驗證**的部署版，不應直接修改 production 檔案救火。
- 確認是否有尚未結束的遊戲，必要時告知玩家服務不穩；保留匿名化故障時間、版本與影響對局量。
- 如果問題涉及密鑰／重連權限，先隔離該服務並換發必要秘密資訊，避免洩漏。
- 回復後執行最小操作 smoke，檢查遊戲房間、勝負判定與版本相容，並寫一份原因與預防措施報告。
- 非相容規則版本的快照不得直接當成已驗證可恢復，需提供 migration 或暫不載入。

## 5. 發布決策的角色責任

- 技術檢查：由開發／測試角色提供客觀 CI 與效能記錄。
- 規則／體驗：由遊戲設計與玩家研究角色提出 A/B 數據及真人操作驗證。
- 風險／預算／個資：由產品所有者確認是否啟用、資料政策與承擔的費用。
- **最後的正式合併、部署、收費與對外公告由遊戲所有者批准。** 本PR維持 Draft。

## 6. 待補強的正式架構

當同時連線、付款或長期玩家帳號增加時，應遷移到外部共享資料庫、支援版本化狀態遷移、與房間寫入交易一致性檢查；不要把單一伺服器的加密檔案當作永久的多人分散式架構。
