## 一、重新定位：第六周目要「看得見，也玩得完」

**本周目有兩條同時推進、但不可互相冒充完成的交付軌道：**

- **A｜實際可玩 UI（P0）：** 在已驗收的 V2 伺服器權威多人對戰上，提供可點選的建房、選王、部署、攻擊、保牌、魔法、國王能力、棄牌與回合結束；不再要求玩家靠瀏覽器原生 prompt 輸入序號。
- **B｜真正看得到的美術樣板（P0 交付）：** 同一兵種**初／中／高三級各一張** Full Art 卡牌概念預覽，**加上一名國王**的立繪＋選擇卡＋戰場資訊框樣板。不是只交美術文字說明，也不是以普通 UI 色塊充當角色美術。

兩條軌道採相同日系奇幻戰略世界觀，卻各自獨立驗收：**兵種卡三張 ≠ 國王套件；圖像概念 ≠ 可編輯正式卡；UI 有畫面 ≠ 已完成對局。**

**收斂策略：** 先產出真正可看的第一張兵種與國王概念，早於大量 UI 微調；再完成基本雙人操作、擴展至 3–5 人。美術採一個兵種跨三階，避免一次嘗試 12 種兵種 × 階級與五名國王導致無法收尾。

## 二、正式兵種卡牌 V1 規範（本次確定）

- 63 × 88 mm、直式、完整 Full Art，歷史王國 × 奇幻戰爭，優雅可愛兼具英氣的高品質日系二次元女性化角色；不犧牲裝備與兵種辨識度。
- 初級／中級／高級對應內部 **AR／SR／SAR 感**，只表現畫面敘事與視覺層次，**不印任何 AR、SR、SAR 或稀有度標記**。
- 獨立四資訊：名稱、**戰力**、**對國王傷害**、**兵種能力**；不憑美術補規則。基準戰力 1／2／3、國王傷害 1／3／5；每張能力文字須以最新 V2 規則資料核對，不能自創特殊能力。
- 正式兵種名稱：步兵、刺客、魔法師、騎兵；程式中 `弓兵`／`法師` 為刺客／魔法師的舊內部代碼。
- **製作必須分層**：角色／背景純插畫不包含規則文字和圖示，名稱／戰力／國王傷害／能力由可編輯 UI／排版層提供。縮小、手機版與實體印刷都需可辨識。
- 可參考收藏卡全圖構圖的通用原則，不可複製其他遊戲的角色、商標、專有卡框、圖案與品牌元素。
- 角色正式定稿前先展示概念並核對；國王歷史人物性別表現尚未決議，**不可擅自視為所有國王都已定為女性**。在國王設計未獲核可前，先提交可替換概念，不冒充定稿。

## 三、五次開發對話：每次都要有可驗證成果

### 第 1 次｜最新技術基線 + 可見美術起稿

**實作：** 核對 GitHub 最新 HEAD 與第五周目餘留的長時間 Chromium CI，定位阻斷回歸。核對 V2 正式兵種資料，定一種兵種供初／中／高卡牌共用。**實際製作並展示至少第一張兵種 Full Art 概念圖與一名國王角色概念圖**，不是只留下 prompt。開始統一 UI 的可點選區域與操作狀態骨架。

**驗收門檻：** 真正存在可檢視的圖像；兩張概念圖清楚標註非正式定稿；房間建立／加入與遊戲狀態仍正常；記錄測試與素材版本。

### 第 2 次｜完成三階兵種卡與雙人 UI 垂直切片

**實作：** 完成選定兵種**初級／中級／高級各一張** Full Art 概念插畫，製作與插畫分離的可編輯四資訊卡面預覽。完成玩家可直接點選部署、選攻擊者、選守方兵種／國王、回應保牌、結束回合的超額棄牌（含秦始皇三抽一放底）。

**驗收門檻：** 可在對話與版本化資料中檢視三張不同階級的角色概念與三張卡面預覽，不得只有文字／空白線框；新 UI 雙 Chromium 從建房到勝者的真實操作成功，或清楚標 P0 失敗。

### 第 3 次｜完成國王三件套、魔法與多人 UI

**實作：** 交付**一名國王**的角色立繪＋選王卡＋戰場資訊框三件可見樣板；數值欄位獨立可改。完成九種魔法的法師／法術／目標點選、五王能力操作、兵種克制提示與錯誤導引；測試保牌與重連後 UI 的恢復。

**驗收門檻：** 三件套圖像／介面預覽可實際檢視；角色與戰場框使用同一視覺元素；九魔法、五王指定流程在新 UI 完成驗證，無原生 prompt 依賴；回歸至少 3 人完整對局。

### 第 4 次｜3–5 人、手機及工程品質驗收

**實作：** 新 UI 驗證 3、4、5 名不同 Chromium 玩家完整對局，彼此手牌保密、回合與淘汰正確；針對 320／375／390／430px 及桌面檢查卡面縮圖、目標、資訊對比與熱區。修復 `client/package-lock.json` 並使用乾淨環境 `npm --prefix client ci`，取得 V1/V2/build 回歸記錄。建立本周目**中期驗收文件**，列出所有美術素材的實際檔案路徑和預覽。

**驗收門檻：** 3–5 人 UI 真實瀏覽器完整對局成功（若失敗要列重現步驟）；基本螢幕尺寸可操作；lockfile `ci` 有成功日誌或標未完成；絕不把上傳提示詞當素材完成。

### 第 5 次｜正式交付、評估、無條件結案

**實作：** 核對最新 HEAD，執行／讀取 `npm ci`、`npm --prefix client ci`、`npm run test:v2`、`npm test`、`npm run build`、真實 2–5 人瀏覽器全流程與重連（工具允許時）。對照清單逐張檢查所有美術輸出是否真正存在、是否分層、是否有錯字／杜撰能力、是否可辨識。提交正式結案文件與素材清單。

**結案門檻：** 當次必交 `docs/v2-cycle6-final-closure-<實際日期>.md`，明列每項 **已驗收／已修改未驗收／未完成／阻礙**、證據、版本、差異、後續接手事項。**無論進度如何，第 5 次對話或期限到達即結案，禁止展延。**

## 四、正式 DoD：兩軌分開評分

### A. UI／技術（P0，缺一即未達標）
- [ ] 2、3、4、5 人透過**新版可點選 UI** 各自完成房間到相同勝者的真實 Chromium 對局。
- [ ] 選王、部署、兵種攻擊、直擊、保牌、抽牌／強制棄牌、九魔法、五王能力、淘汰與結算均可由畫面操作；無原生 prompt／confirm／alert 才能繼續的核心流程。
- [ ] 不洩漏任何對手私有手牌與恢復憑證，伺服器仍為規則與狀態權威。
- [ ] 離線再連後座位、手牌、可操作 UI 狀態一致；既有 V1 正式入口不受影響。
- [ ] 最新 commit 上 V1、V2、build 和主要多 Chromium 回歸有實際成功日誌。

### B. 美術實體（P0，缺一即美術軌未達標）
- [ ] 同一兵種的**初、中、高三張不同 Full Art 角色插畫**，能實際開啟、查看細節、辨識裝備定位和三階敘事差異。
- [ ] 同一三階各有獨立資訊圖層的卡面預覽；**63 × 88 mm** 比例，含名稱、戰力、國王傷害、已核准的能力／標示未核准，不印稀有度。
- [ ] **一名國王**的角色立繪、選王卡與戰場資訊框三件可見作品，並留下未核准項目。
- [ ] 素材路徑、來源／權限、版本、文字數值校對和審核狀態可查，禁止只有文字計畫就宣稱已完成。
- [ ] 插畫內容不烘焙卡面規則文字，正式圖示／文字可單獨修改。

### C. 工程與裝置（P1，應完成或明列原因）
- [ ] `client/package-lock.json` 與 manifest 同步，`npm --prefix client ci` 通過。
- [ ] 320、375、390、430px 與桌面測試記錄卡面文字、HP、回合與操作熱區。
- [ ] 素材的印刷出血與安全區以實際印刷廠規格為準，不擅自宣稱已具印刷廠核可。
- [ ] 明確區分「可看的概念稿」「可編輯合成稿」「正式定稿」「已整合到遊戲」，不互相冒充。

## 五、範圍控制／風險

1. **不量產 12 種兵種／階級、五位國王全套立繪**；本次交付只有一兵種三階及一國王三件套。
2. **不以 AR／SR／SAR 作遊戲內稀有度**，不因畫面華麗而加任何未核准的技能、攻防或費用。
3. 規則未知時只交插畫概念，不虛構數值能力；規則來源以最新 V2 為準，不能用 V1 歷史 DOCX 覆寫。
4. 若 UI 重建與美術工作衝突：**先保障 2 人新 UI 可玩垂直切片 + 實際可見的初階兵種／國王概念**；其餘如未交付就如實判部分達標，不用占用下一周目預支成功。
5. 不處理跨伺服器持久化、Steam／Google Play 發行、排行榜、AI、正式帳號系統等非本次核心目標。
6. 若最新 CI 卡住或排隊，應記錄步驟及耗時；不能推斷為通過，也不能無證據地進行大重構。
7. 不擅自切換正式入口，不刪 V1，不改 `main`。美術創作實際圖像需經使用者可見成果確認，未批准不稱定稿。

## 六、周目管理

- 目前僅**修訂計畫**，第六周目實際開發 **0／5 次**。最多三次必要中斷與五次開發對話為不同計數。
- 第一／二次執行就要有**真正看得見的美術成果**，不能到第四次才發現未製作。
- 每次執行結束列四分類：「已驗收／已修改未驗收／未完成／阻礙」。
- 第四次產出帶素材路徑與 CI 引用的階段驗收紀錄，第五次無條件交正式結案報告。
- 任何變更以最新 Github 分支為依據，不憑前次摘要猜測代碼；commit ≠ test pass ≠ 多瀏覽器試玩 pass ≠ 玩家真人試玩。
