## 一、周目定位與核心交付

**第六周目目標：把已能在 2–5 個 Chromium 用戶端跑完對局的 V2 測試入口，升級為玩家能理解與操作的多人遊戲介面 MVP；同步清除第五周目未結案的回歸風險。**

主要成果必須包含：

1. **P0｜最新多人回歸基線明確化**：確認第五周目最後提交版（或最新開發版）完整回歸結果；若 CI 卡住、逾時或失敗，定位具體阻礙，不讓它阻擋本周目所有工作，但不能標記通過。
2. **P0｜不用輸入數字的主要操作 UI**：以頁面內可見選擇控件，完成部署、兵種攻擊／直擊、保牌、結束回合強制超額棄牌，以及魔法選擇／施法者／對象、國王能力的必要互動。取消遊玩流程對瀏覽器 `prompt`、`alert`、`confirm` 的功能性依賴；操作失敗要有清楚可回復的錯誤訊息。
3. **P0｜新版 UI 仍可完成 2–5 人對局**：同一套伺服器權威規則與私有手牌檢查保持成立；建立／修改實際 Chromium UI 測試，不以只檢查畫面存在代替對局完成。
4. **P1｜可重現安裝與基本設備排版**：修正 `client/package-lock.json`，以乾淨 CI 環境確實驗證 `npm --prefix client ci`，並保留 V1 回歸；320、375、390、430px 及桌面至少覆蓋回合、HP、手牌、目標、棄牌、保牌與錯誤呈現。
5. **P1｜一位國王的美術與 UI 樣板**：交付**一位**角色立繪、選角卡與戰場資訊框的一致樣板；角色性別與歷史擬人化尚未定案，先以經核准的方向或中性可替換 placeholder 呈現，不擅自定稿五位國王的性別；圖示／規則文字不得烘焙在立繪中；記錄素材來源與使用授權。

**不得將第五周目已驗收的 2–5 人多瀏覽器流程視為第六周目 UI 已通過，必須用新 UI 重新操作。**

## 三、五次對話內的執行順序與驗收點

### 第 1 次｜建立乾淨基線與操作介面骨架

- 讀取最新分支、確認完整 CI 是否真正結束；列出失敗點或排隊狀況。
- 盤點 `server/v2-playtest.html` 各原生彈窗與 Socket 事件對應。
- 建立一致的玩家／對手區、回合狀態、選中兵種、操作導引、錯誤訊息區；保留舊測試可辨識的關鍵互動或同步更新測試。
- **交付：** 可進站、建房、加房、選王、開始、看到即時戰場的新版操作骨架，附至少一組瀏覽器驗證。

### 第 2 次｜完成全流程關鍵操作面板

- 完成戰場部署、選擇攻擊對象、國王直擊與保牌回應；完成回合末選擇剛好超額的棄牌，秦始皇三抽一放底。
- 所有必填決策應在頁面呈現，阻止錯誤操作並顯示伺服器回覆。
- **交付：** 新 UI 兩人從建房到勝者的瀏覽器全流程測試成功；不得只憑單元測試。

### 第 3 次｜魔法、五王能力與多人回歸

- 以可見面板選施法法師、魔法、我方／敵方目標與玩家，不使用數字 prompt；五王能力、棄牌與保牌流程整合。
- 改造 3、4、5 人瀏覽器驗收腳本以使用新 UI；同時確認斷線重連後 UI 可恢復。
- **交付：** 九魔法與五王指定 UI 情境、至少一組 3–5 人多瀏覽器對局；若未通過，列出 P0 阻斷清單。

### 第 4 次｜跨裝置可讀性、工程一致性、美術樣板

- 於 320、375、390、430px 與桌面檢查主資訊與操作熱區；修正遮擋和溢位。
- 修復前端 lockfile，驗證純 `npm ci` 安裝、V1/V2 測試、build。
- 交付一位國王的立繪＋選擇卡＋戰場資訊框樣板，**圖層與文字元素可獨立調整**；角色性別與歷史擬人化保持可審核，不擅自確立全部角色。
- **交付：** 完整樣板文件／素材及可辨識的戰場畫面；跑新 UI 的回歸測試。

### 第 5 次｜嚴格驗收並正式結案

- 在任何進一步開發前核對最新 commit 的 CI；優先修 P0 回歸，無法修完則明確列為失敗。
- 取得 `npm ci`、`npm --prefix client ci`、`npm run test:v2`、`npm test`、`npm run build` 的實際日誌（執行環境允許時）。
- 檢查 2、3、4、5 人完整瀏覽器對局、九魔法、五王、重連與手牌隱藏；人工裝置驗收若無真實操作者，不得虛報。
- GitHub 新增 `docs/v2-cycle6-final-closure-2026-11-22.md`（若跨日期，檔名採實際結案日），報告已驗收／已修改未驗收／未完成／阻礙、commit、CI 工作流程及復原途徑。
- **周目結束：** 不論達標與否，第 5 次開發對話結案，不展延。提早到達明定期限則立即結案。

## 五、風險與降級策略

- **長時間 Chromium CI 卡住／排隊：** 先讀 job step 與日誌確認是否真正卡住。等待本身不代表遊戲錯誤；避免無證據的重寫；第 5 次仍準時結案。
- **原生 prompt 被移除導致舊測試失敗：** 同步更新測試為頁面內選擇，逐段遷移；雙人完整對局為優先守護基準。
- **UI 工作影響遊戲規則：** 盡量只改 UI 與必要的展示事件，伺服器邏輯只修 P0；變更後必跑規則回歸。
- **美術定案歧義：** 先提供單角色可替換樣板，未決性別與歷史擬人化不當成已核准定稿；素材權利不明則不進正式產品。
- **時間不足：** 優先保住能操作完整對局的新 UI，降級美術精緻度與次要排版；不能把缺少 P0 的 UI 稱為可玩版。

## 六、不在第六周目硬塞的工作

- 不切換 `main` 與 Render 正式入口，不刪除 V1。
- 不在缺少權限與驗收時擅自完成收費平台服務、Google Play／Steam 上架。
- 不保證第六周目完成跨機器持久化、Supabase 產品化、AI 對手、排行榜、賽季或五位國王所有高完成度立繪。
- 這些是後續周目／發行階段工作，不可以稀釋本周目 P0。

## 七、管理制度

- 每周目最多五次**開發對話**、最多三次**必要中斷**，兩個計數不得混為一談；中斷數不是五次開發對話的提前結案門檻。
- 每次執行結束必報告四分類：「已驗收／已修改未驗收／未完成／阻礙」。
- 每次執行開始前讀取 GitHub 最新檔案，更新當前 HEAD 與 CI，不憑舊摘要推測。
- 只有具證據的正常功能流程才算交付，提交成功≠測試通過≠實際多人瀏覽器遊玩通過。
- 第 4 次執行必建立階段驗收文件；第 5 次**當次**必交付正式結案報告，即使不成功也要結案，不以未來承諾代替。
- 若連續修改只增加失敗而沒有新可玩成果，停止零散修補，盤點前端互動狀態與伺服器事件模型，提出可復現的 P0 架構決策。
